# scripts/

Four files. Three you run, one they all share.

| File | Runs as | Purpose |
|---|---|---|
| `install.sh` | you → re-execs under `sudo` | The **only** privileged step. Copies the runtime, installs both launchd jobs. |
| `uninstall.sh` | you → re-execs under `sudo` | Reverses `install.sh` exactly, including the `/etc/hosts` block. |
| `dev.sh` | you (`sudo` for the helper process only) | Developer loop. Installs nothing. |
| `lib.sh` | sourced, never executed | The launchd labels, paths and markers, defined once. |

`lib.sh` exists for one reason: if `install.sh` and `uninstall.sh` ever disagreed about a
label or a path, uninstall would silently leave a root daemon running. The constants in it
mirror `packages/core/src/paths.ts` (paths, labels) and `packages/core/src/types.ts`
(`HOSTS_BEGIN` / `HOSTS_END`). **If you change one of those TypeScript files, change
`lib.sh` in the same commit.**

---

## Why any of this needs root

Three things in this system are impossible without it, and nothing else is:

1. **Binding `:80` and `:443`.** Ports below 1024 are privileged on macOS. The reverse
   proxy has to own them, because a browser asking for `http://myapp.local` sends the
   request to port 80 — there is no way to express "port 3000" in a hostname.
2. **Writing `/etc/hosts`.** It is `root:wheel 0644`. Name resolution for `myapp.local`
   is a line in that file.
3. **Creating a socket in `/var/run` and installing a `LaunchDaemon`.**
   `/Library/LaunchDaemons` and `/var/run` are root-owned.

Everything else — your config, the alias list, the dashboard, the MCP server — runs as
you, with your privileges, and is uninstallable without a password.

The privilege boundary is deliberately one process (`packages/helper`) and one socket:
`/var/run/localhost-aliases.sock`, created by root and then `chown`ed to **your** uid with
mode `0600`, so no other account on the machine can send it commands. That is why
`install.sh` cares so much about `SUDO_USER`: it re-execs itself with `sudo` rather than
asking you to run `sudo ./install.sh`, and the daemon plist carries
`LA_OWNER_UID=<your uid>`. If it ever recorded `0`, the socket would belong to root and
the dashboard could not talk to the helper.

## `install.sh`

```sh
./scripts/install.sh                 # helper daemon + dashboard agent
./scripts/install.sh --no-agent      # helper daemon only
./scripts/install.sh --trust-ca      # ...and trust the local CA for https://
./scripts/install.sh --uninstall     # hands over to uninstall.sh (flags pass through)
./scripts/install.sh --dry-run       # print every mutating command, run none, no sudo
./scripts/install.sh --prefix DIR    # install into a sandbox tree instead of /, no sudo
```

Run it **as yourself**. It refuses to run on anything but macOS, then re-execs itself
through `sudo` so that `SUDO_USER` identifies the human. Escalating from inside is not
cosmetic: it is what makes the owner uid correct.

What it does, in order:

1. **Preflight.** Checks the source tree, finds `bun`, runs `bun install` and the
   Next.js build (as *you*, never as root — root-owned artefacts in your checkout are a
   nuisance to clean up). A missing dashboard build is fatal only when the agent is
   being installed.
2. **`/usr/local/lib/localhost-aliases`.** `rsync -a --delete` of `packages/{core,helper,mcp,web}`
   and `node_modules`, then `chown -R root:wheel` + `chmod -R go-w`. The daemon must not
   execute code that a non-root account can rewrite, so the installed tree is read-only to
   you. Workspace symlinks under `node_modules/@localhost-aliases/` are rewritten to
   relative paths so they cannot point back at your checkout.
3. **`/Library/LaunchDaemons/dev.localhost-aliases.helper.plist`.** `RunAtLoad`,
   `KeepAlive`, `EnvironmentVariables` = `LA_OWNER_UID` + an explicit `PATH` (launchd hands
   a job almost nothing, so Homebrew's directory has to be spelled out), stdout/stderr to
   `/var/log/localhost-aliases/helper.{out,err}.log`. Written to a temp file in the same
   directory, `plutil -lint`ed, then `mv`'d into place. Loaded with
   `launchctl bootout` (if already loaded) → `enable` → `bootstrap system` → verified with
   `launchctl print system/dev.localhost-aliases.helper`, then it waits up to 10s for the
   control socket to appear.
4. **`~/Library/LaunchAgents/dev.localhost-aliases.web.plist`.** Same treatment, owned by
   you (`chown` to `SUDO_USER` — a root-owned plist in your `LaunchAgents` would be both
   rejected and unremovable without sudo), logging to `~/Library/Logs/localhost-aliases/`,
   bootstrapped into `gui/<uid>`. `RunAtLoad` here means *launch at login*. No GUI session
   right now (SSH, for example) is not an error: the plist is installed and starts at your
   next login.
5. **`--trust-ca`** runs `security add-trusted-cert -d -r trustRoot -k
   /Library/Keychains/System.keychain <caDir>/rootCA.pem`, and only if that file exists —
   the CA is generated by the dashboard the first time you enable HTTPS, so on a fresh
   machine this step tells you to come back later rather than failing.

**Idempotent.** Re-running is the supported upgrade path and the supported repair path:
every step either converges or replaces. Re-running after an edit to the helper is how you
deploy the edit.

Environment overrides: `LA_USER` (owning user shortname, defaults to `SUDO_USER` then the
console owner), `LA_DASHBOARD_PORT` (default 7788), `LA_CONFIG_DIR`, `NO_COLOR`. They are
handed across the `sudo` re-exec explicitly (via `/usr/bin/env`), because `sudo`'s
`env_reset` would otherwise drop them silently — which is the sort of bug that makes an
installer put files in the wrong place.

## `uninstall.sh`

```sh
./scripts/uninstall.sh                          # everything install.sh created
./scripts/uninstall.sh --remove-ca              # ...plus the trusted root
./scripts/uninstall.sh --purge                  # ...plus config, CA key material, logs
./scripts/uninstall.sh --dry-run                # show the /etc/hosts diff, change nothing
./scripts/uninstall.sh --prefix DIR             # operate on a sandbox tree instead of /
```

Also needs root, for the same three reasons, and escalates the same way. It removes, in
this order:

1. `gui/<uid>/dev.localhost-aliases.web` + `~/Library/LaunchAgents/…web.plist`
2. `system/dev.localhost-aliases.helper` + `/Library/LaunchDaemons/…helper.plist`
   (waits for the bootout to actually take effect so `:80`/`:443` are released)
3. `/var/run/localhost-aliases.sock`
4. `/usr/local/lib/localhost-aliases`
5. the managed block in `/etc/hosts`
6. the DNS cache (`dscacheutil -flushcache`, `killall -HUP mDNSResponder`) — without this
   the removed names keep resolving until the cache expires

It is safe to run when nothing is installed: every step reports "already gone" and exits 0.

### The `/etc/hosts` rules

This is the one step that touches a file you did not create, so it is deliberately timid:

- Only the lines from `# >>> localhost-aliases >>>` to `# <<< localhost-aliases <<<`
  are removed. Both markers must match a **whole line, exactly** — `# >>> localhost-aliases >>> foo`
  is your content and stays.
- If the markers are unbalanced (a truncated block, a stray end marker, a nested begin),
  it **writes nothing at all** and tells you to fix it by hand. A guess about where user
  content resumes could eat your hosts file.
- The rewrite goes to a temp file **in `/etc`** (same filesystem), gets `root:wheel 0644`,
  and is `mv`'d over `/etc/hosts` — a `rename()`, so a crash mid-write cannot leave a
  half-written hosts file. If the result would be empty, or identical to what is already
  there, nothing is written.
- The lines about to be removed are printed first.

### The deletion guard

Every directory removal goes through one function that refuses any path which is not
absolute and does not literally end in `/localhost-aliases`. The only paths this script
can delete are:

```
/usr/local/lib/localhost-aliases
/var/log/localhost-aliases              (--purge)
~/.config/localhost-aliases             (--purge)
~/Library/Logs/localhost-aliases        (--purge)
```

plus the two plists and the socket, by exact path. Without `--purge` your config and your
CA (which you may have trusted in other places) are kept; the summary says so.

## `dev.sh`

```sh
./scripts/dev.sh                                   # helper on 8080/8443 + dashboard on 7788
./scripts/dev.sh --privileged                      # the real :80/:443
./scripts/dev.sh --hosts-file /tmp/hosts-dev       # leave the real /etc/hosts alone
./scripts/dev.sh --config-dir /tmp/la-config       # leave your real config alone
./scripts/dev.sh --no-helper                       # dashboard only — no sudo at all
```

Installs nothing, copies nothing, writes no plist. It runs both processes straight out of
the working tree and streams their logs to your terminal, prefixed `[helper]` / `[web]`.
Ctrl-C stops both.

- **Default ports are 8080/8443** precisely so the common case needs no argument. `--privileged`
  is there for when you actually want to test `http://myapp.local` with no port in the URL.
- **`sudo` is asked for once, up front**, with an explanation, and only for the helper
  process — the dashboard must run as you so it writes *your* config. A background
  keep-alive refreshes the sudo timestamp, so shutting down does not prompt again.
- **Ctrl-C really stops the root process.** The helper's pid is recorded by the `sh` that
  `exec`s into it, because `sudo` usually `exec`s the command in place — killing "the sudo
  process" is not a thing you can rely on. Teardown sends `SIGTERM` to that pid, waits 5s,
  then `SIGKILL`s.
- **If the installed daemon is loaded, it refuses to start** and prints the `launchctl bootout`
  command, because both helpers would fight over `/var/run/localhost-aliases.sock` and the
  same ports. `--force` overrides.
- It warns when something is already listening on a port it needs, and warns that the
  helper writes your **real** `/etc/hosts` unless you pass `--hosts-file`.
- If either process dies on its own, the other is torn down and `dev.sh` exits non-zero.

### Environment contract

`dev.sh` passes these to the helper; `install.sh` writes the first two into the plist.
`packages/core/src/paths.ts` already reads `LA_CONFIG_DIR`, `LA_HOSTS_PATH`, `LA_LOG_DIR`
and `LA_DASHBOARD_PORT`.

| Variable | Set by | Meaning |
|---|---|---|
| `LA_OWNER_UID` | install (plist), dev | uid the helper `chown`s the control socket to |
| `PATH` | install (plist), dev | explicit — launchd gives a job nothing usable |
| `LA_HTTP_PORT` / `LA_HTTPS_PORT` | dev only | initial listener ports before the first `ApplyRequest` |
| `LA_DASHBOARD_PORT` | install (agent plist), dev | dashboard port, default 7788 |
| `LA_CONFIG_DIR` | dev `--config-dir` | config + CA directory |
| `LA_HOSTS_PATH` | dev `--hosts-file` | hosts file to rewrite |
| `LA_DEV` | dev | set to `1`; the helper may use it to loosen dev-only behaviour |
| `LA_USER` | you, for install/uninstall | owning user when `SUDO_USER` is not the right answer |

In production the helper gets its real ports from the `ApplyRequest` the dashboard pushes;
`LA_HTTP_PORT` / `LA_HTTPS_PORT` only decide what it binds before the first apply.

## Troubleshooting

```sh
# is the daemon registered, and did it stay up?
sudo launchctl print system/dev.localhost-aliases.helper

# why did it die?
tail -f /var/log/localhost-aliases/helper.err.log

# is the dashboard agent running?
launchctl print gui/$(id -u)/dev.localhost-aliases.web
tail -f ~/Library/Logs/localhost-aliases/web.err.log

# who owns the control socket? (should be you, 0600)
ls -l@ /var/run/localhost-aliases.sock

# what is currently in the managed block?
sed -n '/^# >>> localhost-aliases >>>$/,/^# <<< localhost-aliases <<<$/p' /etc/hosts

# restart the daemon after editing the helper
sudo ./scripts/install.sh
```

`bun: command not found` from the daemon means bun was not where `install.sh` recorded it —
re-run `install.sh` after moving or reinstalling bun. If bun lives in `~/.bun/bin`,
`install.sh` warns you: a daemon that starts before login can fail to reach a home
directory on a FileVault machine. `brew install oven-sh/bun/bun` avoids it.

## Validating changes to these scripts

They run against a real Mac with sudo, so they are checked statically:

```sh
bash -n scripts/*.sh                    # parse with the bash on PATH
/bin/bash -n scripts/*.sh               # ...and with macOS's bash 3.2, which is what
                                        #    /usr/bin/env bash resolves to by default
npx -y shellcheck --shell=bash --external-sources scripts/*.sh
```

Nothing here uses bash 4+ syntax, on purpose: `/usr/bin/env bash` is 3.2 on a stock Mac.

### `--dry-run` and `--prefix`

Both scripts take two flags that exist so the privileged paths can be exercised without
being privileged. Neither asks for sudo, and neither re-execs itself.

`--dry-run` routes every mutating command through `la_run`, which prints it with all
variables expanded instead of executing it. Plist bodies are still rendered and still
passed through `plutil -lint`, and `uninstall.sh` still computes the new `/etc/hosts` and
prints a unified diff of it — it just never renames the file into place. This is the
fastest way to review a change: read the commands it claims it will run.

`--prefix DIR` (or `DESTDIR=DIR`) relocates every absolute system path under `DIR` —
install root, both plists, both log dirs, the control socket, the keychain path and a
mirror of the home directory. Combined with `LA_LAUNCHCTL` / `LA_SECURITY` / `LA_SUDO`,
which point at the real binaries by default, a whole install/uninstall round trip runs
unprivileged against stubs:

```sh
mkdir -p /tmp/stubs && cat > /tmp/stubs/launchctl <<'EOF'
#!/bin/sh
printf 'launchctl %s\n' "$*" >&2
[ "$1" = print ] && exit 113 || exit 0
EOF
chmod +x /tmp/stubs/launchctl

LA_LAUNCHCTL=/tmp/stubs/launchctl ./scripts/install.sh --prefix /tmp/la-sbx
plutil -lint /tmp/la-sbx/Library/LaunchDaemons/dev.localhost-aliases.helper.plist
LA_LAUNCHCTL=/tmp/stubs/launchctl ./scripts/uninstall.sh --prefix /tmp/la-sbx --purge
```

Keep the prefix short: a control socket path over 103 bytes cannot be bound (`sun_path`),
and `install.sh` refuses one in preflight rather than letting the daemon crash-loop.

The `/etc/hosts` transform is worth exercising separately against fixtures — point
`LA_HOSTS_PATH` at a copy and cover: block in the middle, block at EOF, no block,
unbalanced markers, two blocks, CRLF input, and a second run for idempotency.
