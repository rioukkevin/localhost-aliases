# packages/site — update contract

Update the EXISTING site; do not create a second one. Today it has `/`, `/docs`, `/docs/[slug]`
and `/changelog`, and resolves releases from **Vercel Blob**. Five changes:

1. Homepage explains usage with **animated graphics**
2. A **FAQ** page
3. A dedicated **download** page
4. Releases come from **GitHub**, not Vercel Blob
5. Release notes are **generated by AI on push** and become the GitHub Release body

## 1. GitHub replaces Vercel Blob as the release source

`lib/releases.ts` is rewritten against the GitHub REST API for `rioukkevin/localhost-aliases`:

- `GET /repos/{owner}/{repo}/releases/latest` -> version, notes (the release body), published date,
  and the `.dmg` asset (name, size, `browser_download_url`).
- `GET /repos/{owner}/{repo}/releases` -> the changelog list.
- Unauthenticated is 60 req/hr per IP. Use Next's `revalidate` (300s) so a build or a burst of
  traffic cannot exhaust it, and send `GITHUB_TOKEN` as a bearer when the env var is present.
- **It must return `null` / `[]` — never throw — when:** the repo has no releases (today's real
  state: there are no tags), the API 404s or rate-limits, the JSON is malformed, or no `.dmg`
  asset is attached. Every page must render correctly in that state.
- The sha256 lives in the release body (the publish step writes it there). Parse it if present;
  treat its absence as unknown rather than failing.
- Validate the shape before trusting it — a release body is remote input rendered into the page.

Delete the Blob client and `NEXT_PUBLIC_BLOB_BASE_URL`. Remove the Blob upload from the release
workflow. `BLOB_READ_WRITE_TOKEN` stops being a required secret; say so in docs/RELEASE.md.

## 2. Homepage — animated graphics that teach the mechanism

The current hero is an mp4, and the design review found its embedded text illegible at the size it
renders (a 1920 master shown at ~995px). **Prefer inline SVG/CSS animation over video** for the
explanatory graphics: it stays crisp at any width, respects `prefers-reduced-motion` natively, has
no poster/fallback problem, and costs no bandwidth.

Animate the three things that actually explain the product:

1. **The problem** — `localhost:3000`, `localhost:5173`, `localhost:8080` being unreadable, versus
   named hosts.
2. **The mechanism** — a name resolving to a loopback address, then a raw TCP forward carrying
   port 80 to the dev server's port. This is the patch-cable motif from docs/DESIGN.md; reuse it.
3. **What happens on your machine** — the `/etc/hosts` line, the `lo0` address, one admin prompt,
   nothing installed permanently.

Every animation must be paused/simplified under `prefers-reduced-motion: reduce`, must not loop
distractingly behind text, and must degrade to a static, still-legible state with JS disabled.

## 3. FAQ

`/faq`. Answer what a sceptical developer actually asks, in the product's voice, accurately:

- Why not just edit `/etc/hosts` myself? (you still need something listening on :80 per name)
- What exactly runs as root, and for how long?
- Why is it `http://` only — can I get https?
- Why `.test` and not `.local`? (mDNS, ~5s per request, measured)
- Does it work with Vite/Next/Rails HMR and WebSockets? (yes — raw TCP, nothing is parsed)
- What happens on reboot?
- How do I uninstall, and what is left behind?
- Does it phone home? Does it need a network connection?
- Is it signed/notarized? (answer truthfully for the current state)
- Apple Silicon vs Intel.

Every answer must match docs/V2.md, docs/AGENT.md and docs/TLD.md. An FAQ that reassures the reader
with something untrue is worse than no FAQ.

## 4. Download page

`/download`: the current version, the `.dmg` with its size, macOS requirement, **Apple Silicon**
(the tray builds `-target arm64-apple-macos13.0`; there is no Intel binary), the sha256 with a copy
button and one line on how to verify it, and what Gatekeeper will say given the build's real
signing state. When no release exists, show build-from-source instructions instead of a dead
button. Link it from the header and the homepage.

## 5. AI-generated release notes on push

`.github/workflows/release.yml` gains a step, before the GitHub Release is created, that turns the
commits since the previous tag into human release notes and uses them as the release body.

Implementation (`packages/build/release-notes.ts`), per the current Claude API:

```ts
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();           // reads ANTHROPIC_API_KEY
const response = await client.messages.create({
  model: "claude-opus-5",                 // exact id, no date suffix
  max_tokens: 16000,
  system: "...",
  messages: [{ role: "user", content: commitLog }],
});
```

Hard requirements:
- **No `temperature`, `top_p`, `top_k`, or `thinking.budget_tokens`** — all four return 400 on this
  model. Do not add them.
- `response.content` is a union — narrow on `block.type === "text"` before reading `.text`.
- Check `response.stop_reason` before using the result; `"refusal"` and `"max_tokens"` are both
  possible and neither is an exception.
- **Degrade, never fail the release.** No `ANTHROPIC_API_KEY` (forks, secretless runs), an API
  error, or an empty result must fall back to a plain grouped commit list. A release must never be
  blocked because notes could not be written.
- The commit log is untrusted input — a commit message can contain prompt-injection text. Say so in
  the system prompt, and never let the model's output change what gets published beyond the notes
  body.
- Deterministic parts stay in code, not the prompt: the version, the date, the sha256, the download
  URL, and the `Full Changelog` compare link are appended by the script.
- Ask for grouped, factual notes (Added / Fixed / Changed) written for a user, not a commit dump,
  and tell it to omit sections with nothing in them.
- Cache the generated notes as a build artifact so a re-run does not re-bill the API.
