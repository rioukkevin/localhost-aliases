# localhost-aliases v2 — architecture

A full rework. v1 (branch `pre-rework-snapshot`) used an HTTP reverse proxy and a permanently
installed root LaunchDaemon. v2 deletes both.

## The mechanism

DNS maps a name to an IP, never to a port. v2 solves the port half with a **raw TCP forwarder**
instead of an HTTP proxy, and gives every alias its own loopback IP:

```
/etc/hosts        127.0.0.2   myapp.test
lo0 alias         127.0.0.2
forwarder         127.0.0.2:80  ──raw bytes──▶  127.0.0.1:3000
```

Raw byte forwarding, not HTTP. Consequences that make this the KISS choice:
- No `Host` header parsing, no header rewriting, no hop-by-hop header rules.
- WebSockets and HMR work for free — passthrough does not care what the bytes are.
- Any protocol works, not just HTTP.
- **We never see the traffic, so we cannot terminate TLS for project aliases.** Project aliases
  are `http://` only. `https://` works only for the dashboard, because we control that server.
  This is a real limitation and must be stated plainly in the UI, not hidden.

## No permanently installed root component

Nothing is installed into `/Library/LaunchDaemons`. There is no `SMAppService` daemon, no
`sudo` installer script. All privileged work happens in **one batch behind one macOS admin
prompt**, via `osascript -e '... with administrator privileges'`.

`packages/privileged/apply.sh` is the single privileged entrypoint. It is idempotent, takes a
desired-state JSON file, and does exactly four things:

1. add/remove `lo0` aliases (`ifconfig lo0 alias|-alias <ip>`)
2. rewrite the managed block in `/etc/hosts` (markers preserved byte-for-byte outside them)
3. flush DNS (`dscacheutil -flushcache`, `killall -HUP mDNSResponder`)
4. (re)start the forwarder as root

The user is prompted when the hostname/IP set changes — i.e. on adding or removing an alias, and
once at app launch if the live state has drifted (a reboot clears `lo0` aliases). Changing only a
target **port** does not need a prompt: the forwarder watches its routes file and reloads.

### How a root process is stopped without root

The forwarder runs as root but must not outlive the app, and a user process cannot kill root.
So the forwarder owns its own lifetime: it watches a **liveness file** the app touches every few
seconds. If the file is stale or removed, the forwarder exits on its own. Quitting the app is
therefore clean with no prompt.

## Processes

| Process | User | Lifetime | Job |
|---|---|---|---|
| tray (Swift) | you | app | menu bar, spawns the dashboard, triggers privileged applies, heartbeat |
| dashboard | you | app | **embedded in the bundle**, Next.js on 127.0.0.1:<high port>, UI + API |
| forwarder | root | app | raw TCP `lo0-ip:80 → 127.0.0.1:port`, exits when the heartbeat stops |
| mcp | you | per client | stdio MCP server, talks to the dashboard API |

The dashboard is **never** run outside the app in production. `bun run dev` stays available for
development only.

## Reserved alias: the dashboard itself

`index.test` is reserved and always present. It maps to the first loopback IP and forwards to the
embedded dashboard's port, so the tray's "Open Dashboard" opens `http://index.test` rather than a
port number. It cannot be deleted or renamed from the UI.

## The TLD: `.test`

Aliases are `<name>.test`. `.test` is reserved for development by RFC 6761 — never delegated,
never publicly resolvable, and not claimed by anything on macOS, so the `/etc/hosts` entry is the
answer immediately.

`packages/core/src/tld.ts` owns the rule — one list per reason, and each rejection returns its
own message. Three families are rejected by validation and never offered in the UI:

- **`.local`** — reserved for mDNS by RFC 6762 and owned by `mDNSResponder` on macOS. Every
  lookup waits out a multicast query: ~5s per name, measured, *whether or not the name is in
  `/etc/hosts`*. The suffix is the cost, not our hosts block.
- **HSTS-preloaded TLDs** (`.dev`, `.app`, `.page`, …) — Chrome and Safari upgrade `http://` to
  `https://` before the request leaves the machine. Project aliases are `http://` only by design
  (a raw TCP forwarder cannot terminate TLS), so those names would fail with a misleading TLS
  error.
- **`.localhost`** — macOS answers it as `127.0.0.1` itself, ignoring `/etc/hosts`, so the name
  would never reach the alias's own `127.0.0.x`.

The UI offers `test`, `internal`, `lan`, `home.arpa` and `example`. Numbers, method and the
reproduction commands: [TLD.md](TLD.md).

## Loopback IP allocation

`127.0.0.2` … `127.0.0.254`. `127.0.0.1` is never used (it is the real loopback). The lowest free
address is assigned at creation and stored on the alias, so an alias keeps its IP for life. 253
aliases is the ceiling; the UI says so if it is ever reached.

## Bundle layout

```
LocalhostAliases.app/Contents/
├── Info.plist                     LSUIElement, dev.localhost-aliases.app
├── MacOS/LocalhostAliases         Swift tray
├── Resources/
│   ├── bin/bun                    embedded Bun runtime
│   ├── dashboard/                 next build --output standalone (+ .next/static, public)
│   ├── forwarder                  bun --compile, runs as root
│   ├── mcp                        bun --compile, stdio MCP server
│   └── privileged/                apply.sh (the one privileged entrypoint), uninstall.sh,
│                                  lib.sh, teardown.sh, self-delete.sh — the last two are
│                                  why the app can uninstall itself with no source tree
```

## Packages

- `packages/core` — pure domain. Alias model, config store, `/etc/hosts` block rendering, loopback
  IP allocation, desired-state building. No side effects at import.
- `packages/forwarder` — raw TCP forwarder. Reads routes JSON, binds each `ip:80`, splices sockets,
  watches the liveness file. Compiled with `bun build --compile`.
- `packages/privileged` — `apply.sh` plus the osascript wrapper that raises the admin prompt, and
  `teardown.sh` + `self-delete.sh`, the whole uninstall.
- `packages/dashboard` — Next.js app (UI + API routes). Design carried over from v1 verbatim.
- `packages/mcp` — stdio MCP server against the dashboard API.
- `apps/tray` — Swift menu-bar app.

## Testing

**Unit tests only** (`bun test`). No Playwright, no e2e. The highest-value targets: hosts block
transforms, IP allocation, desired-state diffing, forwarder route parsing and socket splicing
(against loopback servers on unprivileged ports), config store CRUD.

No test may touch `/etc/hosts`, `lo0`, `~/.config/localhost-aliases`, or run any privileged command.
Use `LA_*` env overrides and ports above 1024 everywhere.

## Onboarding

One flow with visible progression, automating everything it can:
1. explain exactly what will change on the machine, before anything happens
2. one admin prompt → apply hosts + lo0 + start forwarder
3. verify by actually fetching `http://index.test` and reporting the result
4. optional: generate a local CA and trust it in the **login keychain** for `https://index.test`
   (a user click; Firefox uses its own store and is called out)
5. optional: install the MCP server into Claude Code / Codex

Re-runnable from Settings. Every step shows its real state, never an optimistic one.

## Uninstall

One implementation, three entrances. `packages/privileged/teardown.sh` is the whole teardown and
is **shipped inside the bundle**, because removing an installed app must not require a checkout
of its source. `make uninstall`, the tray's "Uninstall…" item and the dashboard's settings drawer
all run that one file.

In order: one admin prompt → the bundled `uninstall.sh` as root (stop the agent, drop our `lo0`
addresses, strip the `/etc/hosts` block, flush DNS, and hand back every file root created in the
user's directories); then, unprivileged, the CA out of the login keychain by fingerprint,
`~/.config/localhost-aliases`, `~/Library/Logs/localhost-aliases`, and finally the `.app` itself.
Nothing is left behind.

Three rules the implementation exists to hold:

- **Whoever creates a root-owned file cleans it up.** Root writing `logs/privileged.log` into the
  user's config directory is what made an unprivileged `rm -rf` fail with `Permission denied`.
  `lib.sh` chowns at the point of creation, and `uninstall.sh` sweeps the tree before it gives up
  root.
- **Report and continue, never abort.** That same failure stopped the old script before the step
  that removes the app, leaving an app that had already dismantled its own system state. Every
  step now reports `ok`/`failed`/`skipped` and the sequence runs to the end. A *cancelled*
  password prompt is the one exception: it stops, and removes nothing.
- **A running app cannot delete its own bundle.** `self-delete.sh` is copied out of the bundle
  into a scratch directory, spawned detached, waits for the app's pid, then removes the bundle —
  and refuses any path that is not our bundle.
